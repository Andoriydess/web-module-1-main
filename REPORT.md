# Модуль 1. Рефакторинг та аналіз Web API

## Рішення щодо рефакторингу

### Модулі

Початковий монолітний файл `app.js` було розділено на три модулі:

* `orders.js` — збереження замовлень у масиві та операції додавання, пошуку, видалення й отримання записів.
* `services.js` — бізнес-логіка: валідація даних, обчислення суми `total`, нормалізація та генерація ID.
* `app.js` — налаштування Express, middleware, обробка HTTP-маршрутів (`/health`, `/orders`, `/orders/:id`), глобальна обробка помилок і запуск сервера.

Напрямок залежностей: `app.js` → `services.js` → `orders.js`.

* **HTTP-логіка** (`app.js`): зчитування параметрів, вибір кодів відповіді (`200`, `201`, `204`, `400`, `404`), формування заголовків (`Location`) та надсилання JSON.
* **Бізнес-логіка** (`services.js`): перевірка полів, валідація цін та кількості, розрахунок загальної суми замовлення.

### API-контракт

Усі HTTP-маршрути, методи та формати відповідей збережено:

| Маршрут | Метод | Очікувана поведінка |
| --- | --- | --- |
| `/health` | GET | Status 200, стан сервера та версія API |
| `/orders` | POST | Status 201, створення замовлення та заголовок `Location` |
| `/orders` | GET | Status 200, масив замовлень та `count` |
| `/orders/:id` | GET | Status 200 із замовленням або 404 |
| `/orders/:id` | DELETE | Status 204 без тіла або 404 |

**Перевірка:** Команда `npm test` підтвердила збереження контракту — успішно пройдено **4 з 4** тестів (`pass 4, fail 0`).

| Показник | До | Після |

| p99 | ~2002 мс | ~25 мс |
| Пропускна здатність | ~20.7 req/s | ~2873.3 req/s |

- **Найповільніші ендпоінти**: POST /orders та GET /orders/:id були найповільнішими через наявність функцій зі штучною затримкою synchronizeOrderState() (пауза 900–2000 мс). Оскільки збереження виконується в оперативній пам'яті синхронно, ця затримка є штучною.
